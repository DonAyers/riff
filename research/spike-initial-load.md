# Spike: a smooth, fast first load

Date: 2026-10-07. Exploratory, nothing committed until Don picks.

## What actually happens on load today

Measured on a production build (`vite preview`) in Chromium with 6x CPU throttle and a slow mobile network, screencast frame by frame plus `layout-shift` and `paint` observers. (Filmstrips were shared in the project thread.)

| Time | What the user sees |
|---|---|
| 0 ms | Blank white (no HTML yet) |
| ~600 ms | First paint: a **cream (light) page**, even in dark mode. CSS has loaded but the theme and palette are only set by JavaScript. |
| ~1.8 s | Page turns **dark** once the 200 KB (gzip) entry script runs `initializeThemePreference()`. |
| ~2.0 s | First content, drawn in the **fallback fonts** (Courier New / Arial): "Riff", "Record", "00:00". |
| ~2.0–2.6 s | Fonts swap in one by one: Silkscreen headings, then Atkinson body text (lines re-wrap), then VT323 last, so the **timer visibly shrinks**. |

Cumulative Layout Shift is tiny (about 0.002), so this is not classic layout shift. The "odd jumping" is two things: a **theme flash** (light → dark) and a **three-step font swap** (FOUT). Both are visible without throttling too, just faster.

Causes in the code:
1. `index.html` has no theme or background until `main.tsx` runs (`src/hooks/useThemePreference.ts`, `usePalettePreference.ts`), and `theme-color` is hard-coded.
2. `@fontsource` CSS uses `font-display: swap` and the fonts are only discovered after the main CSS is parsed. Nothing preloads them.
3. The entry bundle carries every route: react-dom (expected), but also `svguitar` (~300 KB source), `smplr` (~120 KB), `pitchy`, the looper and the builder. The Record screen needs none of those, and it all has to download and parse before the first pixel of content.
4. The page is an empty `<div id="root">` until React renders, so nothing meaningful paints before the JS runs.

## What the docs and tried-and-tested code say

- **No theme flash:** set `data-theme` / `data-palette` from `localStorage` in a tiny *blocking* inline `<script>` in `<head>`, before any CSS paints. This is the pattern `next-themes` and most theme switchers use. Add `<meta name="color-scheme" content="light dark">` so the browser's own canvas matches before CSS arrives.
- **Fonts without jumps** (web.dev):
  - `<link rel="preload" as="font" type="font/woff2" crossorigin>` for the few fonts above the fold, so they're fetched alongside the CSS instead of after it.
  - Preload + `font-display: optional` is "the most effective way to guarantee no layout jank": Chrome holds the first render up to ~100 ms for a preloaded optional font, then never swaps.
  - For text that must use the brand font (Silkscreen title, VT323 timer), `font-display: block` on a tiny preloaded font is acceptable: the files are 8–18 KB and the service worker precaches them, so return visits are instant.
  - `size-adjust` / `ascent-override` fallback faces (generated by `fontaine` for Vite) make the body-font swap near invisible. They help little for the pixel fonts, whose shapes are nothing like Courier.
- **Less JS before first paint** (Vite docs): `React.lazy` + dynamic `import()` per route splits the bundle; Vite adds modulepreload for the chunk's dependencies and loads each chunk's CSS before it evaluates, so no unstyled flash.
- **Paint before JS** (optional, bigger): prerender the Record shell to static HTML at build time and `hydrateRoot` it, or put a static header and tab bar skeleton in `index.html`.

## Proposal (ranked)

1. **Theme and palette before first paint.** An inline head script reads `riff:theme-preference` / `riff:palette` (same keys as today), sets `data-theme`, `data-palette` and `theme-color`. Plus `color-scheme` meta and an inline `html { background }` per scheme. Removes the light → dark flash. Small, no risk.
2. **Fonts load once, no visible swap.** A small Vite plugin injects `rel=preload` for the hashed Silkscreen, VT323 and Atkinson 400 files; `@font-face` overrides set `block` for the two display fonts and `optional` (with a metric-matched fallback via `fontaine`) for body text. Removes the three-step swap and the shrinking timer.
3. **Route-level code splitting.** Lazy-load Builder, Tuner, Looper and Settings, and the fretboard/sampler, behind `Suspense` with a fallback sized like the page. Shrinks the critical bundle substantially (exact gain measured once split), so content appears sooner on slow phones.
4. **Static app shell** (optional): header and tab bar in `index.html`, or full prerender of `/`. Biggest FCP win but most moving parts (hydration must match the theme and onboarding state).

Every item gets a Playwright check that records the load and fails on a theme change after first paint, or a font swap after first contentful paint, plus Vitest for the head script logic.

Recommendation: do 1 to 3 together in one PR (they are independent and each small), measure again, then decide whether 4 is worth it.

## Decision and result (2026-10-07)

Don picked items 1 to 3. Built as:
- `src/lib/themeBoot.ts`: a self-contained `bootTheme()` that a Vite plugin (`firstPaintPlugin` in `vite.config.ts`) inlines after the `theme-color` meta. A `color-scheme` meta is also added.
- `src/styles/fonts.css`: our own `@font-face` rules (WOFF2 only) with `block` for Silkscreen and VT323 and `optional` for Atkinson. The same plugin preloads the hashed files (`src/lib/fontPreloads.ts`), and the build fails if one is missing. `fontaine` was not needed: `optional` never swaps, so there is nothing to metric-match.
- `React.lazy` for Builder, Tuner, Looper, Settings and the chord map, and `smplr` is loaded on first playback. Tabs show a sized, screen-reader-labelled placeholder for the rare slow first load. The service worker still precaches every chunk.

Same throttled measurement after the change:

| | Before | After |
|---|---|---|
| Entry script (gzip) | ~200 KB | ~99 KB |
| First paint | light, then dark at ~1.8 s | dark (the saved theme) |
| First contentful paint | ~2.0 s | ~1.6 s |
| Font swaps after first content | 3 | 0 |
| CLS | ~0.002 | 0 |

Item 4 (static shell / prerender) is not needed for now.
